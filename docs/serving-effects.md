# Paid beverage effect restrictions

`com.bettercontent.betterdrinkingwater.api.ServingEffects` is a registration-only integration seam. Drinking Water does not depend on a cooking/policy provider. With no provider registered, selected effects are unchanged.

## Public contract

```java
record Selected(ResourceLocation id, int duration, int amplifier) {}
record Bounds(boolean suppress, int maxDuration, int maxAmplifier) {}
interface Rule {
    Bounds restrict(ResourceLocation paidSourceId, Selected selected);
}
ServingEffects.register(ResourceLocation owner, Rule rule);
ServingEffects.freeze();
Optional<Selected> result = ServingEffects.restrict(paidSourceId, selected);
```

`Bounds.IDENTITY` preserves the validated native entitlement; `Bounds.SUPPRESS` removes only the selected effect. Duration bounds are 0..1,200,000 ticks and amplifier bounds are 0..31, matching the existing persisted-entitlement limits. Zero duration suppresses. A selected effect must have positive duration. Rules can only reduce duration/amplifier or suppress; effect identity cannot be changed and bounds cannot increase an entitlement.

Register before any paid entitlement is read or purchased. The cooking consumer registers in its mod constructor. Once all setup registrations are complete, explicitly freeze. The first `restrict` also freezes automatically. Duplicate owner IDs, nulls, late registration, invalid limits, null results, and compounding/non-idempotent provider rules fail rather than silently changing paid reserves. There is no runtime reset/unfreeze API. Distinct providers compose by minimum bounds independent of registration order.

Rules must be deterministic, pure, idempotent, and server-safe. No inventory access, payment, random draws, effect application, or player mutation is permitted. The argument is the **actual persisted paid serving source ID**, not a fabricated/default item stack; the existing reserve stores that ID rather than a complete original stack. The selected effect is an immutable value after native probability/group draws and harmful amplifier selection. Providers must not infer unrecorded item NBT.

For example, the consumer may resolve the actual registered effect and preserve harmful/non-beneficial effects before applying beneficial restrictions:

```java
ServingEffects.register(new ResourceLocation("better_cooking", "beverage_effect_caps"), (source, selected) -> {
    var effect = ForgeRegistries.MOB_EFFECTS.getValue(selected.id());
    if (effect == null) throw new IllegalStateException("Missing selected effect " + selected.id());
    if (!effect.isBeneficial()) return ServingEffects.Bounds.IDENTITY;
    if (suppressedBeneficialIds.contains(selected.id())) return ServingEffects.Bounds.SUPPRESS;
    return new ServingEffects.Bounds(false, 1200, 0);
});
```

The consumer owns actual classification and the suppression set. Drinking Water adds no hardcoded cooking IDs, chance changes, or inverse dependency.

## Entitlement/payment boundary

`BeverageServing.purchase` retains its original native chance/group roll loop, signed-group sharing, booze/dread-nog amplifier selection, and original subsequent validator call. Only `BeverageServing.read` is extended: after validating **all original** effect IDs, providers, duration/amplifier bounds, and duplicate effects, it applies the restrictions before publishing the immutable serving. Even a suppressed effect must pass original validation; restrictions cannot conceal a removed provider or malformed reserve.

Fresh purchases already pass through this read path after selection. Existing paid reserves use the same read path without new probability draws, amplifier accumulation, payment, or container debit. Idempotent caps cannot compound during repeated saves/reads. Incompatible policy callbacks are rejected. An effect suppressed by an earlier policy is never regenerated by a later read.

The original source ID, hunger, saturation, nutrition, action, paid reserve fraction, and container accounting are unchanged. No hydration tracker, reserve ledger, or food-receipt implementation is added or modified. Effect release still uses the original `from`/`to` fractions and cadence management. Already-consumed fractions are never replayed; newly capped total durations govern only subsequent releases. This does not retrospectively remove or downgrade an already-active effect.

`BeverageEffects` is deliberately unchanged: an active infinite effect or stronger amplifier is preserved; an existing equal-amplifier effect with a longer duration is not shortened. New caps also cover its direct-duration-update path because the entitlement is bounded before release, not merely intercepted at `addEffect`.
